# A18 独立交付账本审查

审查：`backend/delivery.py`、`scripts/audit_delivery.py`、`tests/test_delivery.py`；交叉核对 `app.py`、`trace.py`、`oracle.py`、`audio.js` 和 `DeliveryReview.vue` 的事件生产/消费。已读仓库约定、README、CONTRACT、统一协议及当前执行/Jarvis更新。

1. **P2：缺少播放证据被归为“未开始”。** `backend/delivery.py:51-56` 默认 `playback_status='not_started'`；84-85 行又把旧 `playback_end` 中缺失的 `started/played_samples` 当作否定事实。普通触发：服务端已收到音频，但归档/报告生成时尚无浏览器回执，或审查不含采样字段的旧记录。无法区分“确实未播”和“观测缺失”，UI 会直接显示 not started（`DeliveryReview.vue:26-28`）。`tests/test_delivery.py:10-18` 还固化此结论。最小修正：无回执使用 unknown/pending，只有明确 `started=false` 且零播放样本时才记 not_started；保留旧记录未知值。

2. **P2：Undo/Restore 的合法发布不进入交付账本。** `backend/delivery.py:31-43` 仅收集 `tool_committed`；普通点击撤销/恢复会实际调用 `store.restore`，以独立 `undo/restore` 事件记录新 revision/state（`backend/app.py:805-811`）。报告因此有对应渲染，却无该次提交，无法完整审查用户修订后的公开状态。最小修正：将这两类已有发布事件纳入 commits，保留 actor/action 和新版本；不把它们计为模型成功。

离线复现：以 `.venv/Scripts/python.exe -B -` 直接调用纯函数，无服务/API/测试套件。输入与实际输出：

```text
audio_received(r1, sample_start=0, sample_end=2400)
=> received_audio_samples=2400, playback_status=not_started, playback=null
playback_end(r1, details={interrupted:false})
=> measurement=unknown, playback_status=not_started
undo/restore(revision=8,state={views:[v1]}) + chart_rendered(revision=8,v1)
=> 各自 commit_count=0, surface_count=1
```

其余窄范围结论：中断标记优先于空队列完成（80-83 行），渲染和暴露分列；生成文本不充当已播放文本。数值审计按实际 source 独立重算，未支持维度保持 not_checked；人工语义/听取保持 pending。未发现这些部分把数值一致直接当成意图正确。完整意图评分仍属协议明确待完成项，不列代码缺陷。本轮未调用真实模型、未验证实际听感、未修改源码或既有证据。
