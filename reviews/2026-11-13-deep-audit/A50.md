# A50｜研究重点与最小交付

已读 AGENTS、README、TASKS、CONTRACT、DESIGN_REVIEW_BRIEF、UNIFIED_RESEARCH_PROTOCOL、REAL_API_FINDINGS、GOAL_EXECUTION、ACCEPTANCE、中文论文；核对 app.py、revisions.py、App.vue、RevisionPanel.vue 及既存界面截图。未读其他 Axx，未启动服务、调用 API 或改代码。

1. **P1｜研究取舍：聚焦用户对修订范围的理解与纠正。** 最合适的问题是“显式分开对象来源、当前目标/修改、保留/解除条件，是否帮助用户理解并纠正修订，代价多少”。直接与绑定路径共用指令（`backend/app.py:195–216`）、成员解析与编译（`backend/revisions.py:136–152`），明确请求直接提交（`backend/app.py:390–395`）。因此没有用户介入的首次工具成功率不能归因于卡片。可主张三段表示和执行/交付核验链已实现，并有有限真实可行性例证；不能主张绑定算法更强、卡片提高模型正确率或全双工优越性。以理解及最终修订正确性为主要结果，修复成本为次要结果；无需新模态实验（统一协议:19–30、74–90）。

2. **P1｜实证缺口：投稿主张需要真实用户证据。** 八次诊断4次目标正确、原驱动仅3次通过（`docs/REAL_API_FINDINGS.md:11–20`）；后两次一成一败，类型错误仍在，旧竞态未触发、图像修复只有本地验证（`paper/cscwd_zh/main.tex:203–210`）。这些记录不能组成卡片因果效果。最小下一交付是冻结同模型/工具/历史策略/预算的 B0/B2 实际呈现，先完成业务材料与语音窗口的可行性检查，再由独立标注者先定用户意图、后查结果，收集理解和修复证据，保留失败与未知（同论文:216–242）。软件通过不能填补该缺口；当前稿仍是机制与技术诊断稿，不保证录用。

3. **P1｜前端呈现缺口：先让研究处理在主屏可检查。** 普通明确修改后，摘要仅显示视图数量、历史版本及泛化提示（`frontend/src/App.vue:579`）；实际改变与保留值在遮挡画布的详情抽屉（同文件:603–608；`components/RevisionPanel.vue:79–85`）。用户不展开便看不到三段核心内容，影响处理是否真正到达用户。优先把现有 card 数据呈成紧凑、非阻塞三段摘要：来源版本/成员、具体图号/修改、保留与解除的值，并通向现有纠正入口；明确请求不新增确认。按 DuplexVis 英文三图/对话布局融合，在1920/2560 CSS宽度核对图表与摘要同时可读。保留集合复用和独立范围，不以自动联动、三入口改造或新增面板替代这一交付。
