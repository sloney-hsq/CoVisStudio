# 新增用户设计：融合审查依据

用户在本轮审查中补充 DuplexVis 前端设计，要求智能判断重点方向与应改之处。继续完成 50 代理审查；当前为设计/源码审查，不据此直接改应用代码。

用户给出的设计要点：英文产品界面，名称 DuplexVis；左侧 Workspace/Study sessions/Diagnostics，中间 Olist 三图（订单量、低评分率、配送天数），右侧 Co-pilot。浅灰背景/白卡/少量紫色，稳定的品类身份配色。原文以 1440×900 画布、1920×1080 适配，侧栏208、助手320、图卡约264×280–300。此前用户固定27寸4K屏幕，审查应考虑系统缩放后的1920/2560 CSS宽度，不把物理像素直接当CSS像素。

正常功能：地区和时间范围；Linked views 开关联动修改地区/类别，独立时每图显示真实范围；选图、跨图选品类高亮，选择不筛选；Top N 动态排名 vs Fixed/pinned 精确成员；Keep this group 只固定类别，不恢复旧数值/范围；Edit view 修改标题/指标/地区/排序，保留其他条件。数据表按品类对齐，缺失不当零；At a glance 一句非因果事实；近期修改/历史/Undo/Restore；语音状态及输入上下文。

设计还提出 Text / Turn-based / Realtime 三入口、研究者连接配置、任务选择/计时/完成/导出、诊断回放时间线。当前统一研究协议只有同一 full-duplex 环境中的 direct/B0 与 bound_revision/B2，三模态不是当前研究自变量。新设计缺少作为主处理的三段式修订卡；不要在融合时抹掉已有研究核心，也不把所有条件都自动联动修好而消除研究目标。明确编辑目标、联动范围及固定集合规则。

需要判断的具体问题：

1. 保留成熟分析工具的三图/对话/集合工作流；研究聚焦用户可检查和纠正的“对象来源—当前目标与修改—保留/释放条件”。同模型指令和compiler下，卡的收益须经用户实际查看/纠正产生，不能把脚本API成功率差异当卡的因果效果。
2. 自动联动应为共享且显式的普通工具，不能把手动选择等同筛选。全局范围显示混合时不能仍写单一SP；局部修改和保留未选图仍要成立。
3. 参与者不需要研究条件、策略、执行轨道、SK配置或原始日志；研究者页独立。暂不增三模式正式实验、通用企业平台或任意配置体系。
4. `Current dashboard attached` 只在实际对应版本发送后成立；连接、工具提交、渲染与完成文案分开，不能提前确认。稳定颜色按类别身份，时间趋势按时间连接。
5. History要区分“复用这组类别”和“恢复整份配置”；非阻塞修订卡明确这次改了什么、保留什么，普通明确请求不新增必点确认。
6. 主屏优先图、当前范围、选择与修订反馈。数据表/日志次级，避免侧栏+窄图+长聊天挤压主图。不要为制造反馈价值自动指出用户合理分步产生的中间差异。

本文件是用户长文的忠实任务摘要及主审的待检验融合方向；不是用户已批准的实现规格。相关前端代理应给最小必要改动，不扩展架构。
